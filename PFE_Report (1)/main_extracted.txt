General Introduction
With the rapid expansion of network infrastructures, cybersecurity has become central to an
organisation’s resilience in the digital age. Firewalls are the first line of defence and must be
properly managed and configured to safeguard sensitive data from the ever-evolving threat
landscape. Traditionalmethodsoffirewalladministration, whichrelyonmanualcommand-line
input and complex graphical user interfaces, cannot meet the speed and complexity demanded
by modern networks.
The most significant challenge to network administration today is the "semantic gap" be-
tween high-level security goals and low-level technical implementation. The security adminis-
trator’s intent must be translated into vendor-specific syntax (i.e., configuration rules) manu-
ally, and this is not only a lengthy process but also very error-prone. A small misconfiguration
of a security policy can result in a serious vulnerability and/or a disruption of service.
This final-year project, carried out atKleos Tunisia, addresses these inefficiencies at the
intersection of Artificial Intelligence and Network Security. The main goal is to develop and
implement a hybrid AI-assisted administration agent forFortinet FortiGatefirewalls. We
propose a system that leverages Large Language Models (LLMs) and Retrieval-Augmented
Generation (RAG) to enable administrators to interact with infrastructure through natural
language.
The innovation of the project lies in its multi-layered approach:
•Natural Language Processing:Understanding administrative intent in English and
French with the Mistral model.
•Grounding in context:Implement a RAG mechanism based on ChromaDB to ensure
that all generated configurations strictly follow the official Fortinet technical documen-
tation.
•Security and Verification:A rigorous validation pipeline and human-in-the-loop

1.1 Introduction
AutomationandIntent-Based Networking (IBN)are driving modernization of the en-
terprise network infrastructure. In highly dynamic security environments, firewalls are an
important enforcement point for security postures and require constant and accurate admin-
istration. The complexity of network management is due to the huge number of low-level
device configurations, as shown in the seminal work by Benson et al. [1]. In the past, net-
work admins had to manually configure these devices, either through command-line interfaces
(CLIs), graphical dashboards or static infrastructure-as-code (IaC) scripts. But at the scale
of infrastructure and more dynamic operational needs, the cognitive load on administrators
becomes much more significant. Configuration drift or delayed incident response from a cog-
nitive burden is common; indeed, empirical analyses by Oppenheimer et al. [2] suggest that
human configuration errorremains the primary driver of major internet service outages.
Embeddingconversational artificial intelligenceinto infrastructure engineering is a
potentially disruptive paradigm shift in the administration of systems. AdvancedNatural
Language Understanding (NLU)capabilities enable direct translation of abstract human

Large Language Models (LLMs) can generate network commands effectively, but guarantees

1.3 Existing System Analysis
The operational management of FortiGate appliances varies betweenmanual intervention
andstatic automation. Manual administration through FortiOS allows for nuanced deci-
sions, but is inherently slow and prone to human error. In a detailed study of routing anoma-
lies, Mahajan et al. [4] demonstrated how small configuration errors can trigger cascading
global effects. Static automation frameworks (e.g. Ansible or Terraform) on the other hand
guarantee configuration consistency, but at the cost of considerableoperational rigidity.
Static policy-based systems such as CFEngine pioneered by Burgess [5] demand significant
domain-specific expertise and are not designed to dynamically adapt to ad-hoc administrative
queries or real-time conversational troubleshooting.
Recent attempts to introduce generic conversational agents into the network operations

1.4 Problem Statement
The key challenge in modern network orchestration is not only executing commands but also
understand intent correctly and reconciling with live operational environment safely. IBN re-
quires a continuous closed loop thattranslates, activates and verifiesintent against active
system state according to Leivadeas and Falkner [7]. While human error remains the main
cause of security outages, critical infrastructure state transitions cannot be blindly trusted to
fully automated, probabilistic systems. Recent work in software-defined networking empha-
sizes the importance of validating configurations before deployment to avoid severe connectiv-
ity loss.
The main problem studied in this thesis is:how to build a conversational administration
prototype that reduces FortiGate operational workflows with AI-assisted natural language un-
derstanding, while adhering to strictdeterministic orchestration,active state synchro-
nizationandverifiable infrastructure-as-codeprinciples for configuration changes?

1.6 Proposed Solution: Deterministic AI-Assisted Or-
chestration
We propose a solution in the form of a hybrid network orchestration prototype supported by
NLU, specifically tailored to FortiGate environments. The system takes in natural language
queries and routes them through a controlled routing pipeline. Routine operational queries
and searches of documentation are passed through aRetrieval-Augmented Generation
(RAG)architecture. RAG, as initially introduced by Lewis et al. [9], integrates pre-trained
language models with dense vector retrieval to deliver precise, grounded, and contextually
rich responses without the need for model retraining. RAG-enhanced architectures have been
shown to be highly effective for parsing technical documentation and log files in network
operations [10]. For administrative mutations, a dedicated NLU engine extracts structured
intent that is immediately handed over to a deterministic Python orchestration backend. This
control plane performsentity reconciliation,forward-looking compliance checking,
Human-in-the-Loop (HITL) approvalandtransactional API execution. The plat-
form is a hybrid AI-assisted operations assistant, streamlining the administrator’s workflow
and enforcing strict security standards.

1.10 High-Level Grounding Concepts
A primary engineering issue encountered in intent-based orchestration systems is converting
vague human references into strict infrastructure identifiers. This semantic conversion pro-
cess is accomplished by theGrounding Engine. For instance, if an administrator requests
to "block traffic from the web servers," then the NLU will extract the entity concept. Fol-
lowing this extraction, the deterministicreconciliation enginequeries the live FortiGate
state to obtain the exact address object names or IP subnets needed by the underlying API
corresponding to "web servers."
Ifanentitycannotbedefinitivelyresolvedagainsttheliveinfrastructurestate, orifrequired
operational parameters are missing, the system initiates aConversational Clarification
Loop. This workflow ensures the platform behaves as a collaborative administrative assistant,
persistently requesting specific context until the intent is deterministically sound.

1.12 Validation & Compliance Strategy
Before any configuration payload reaches the execution layer, it is subjected to a multi-tiered

detailed in the architectural design sections of Chapter 3.
1.13 Infrastructure Lifecycle Management
Whileconversationalinterpretationformstheprobabilisticlayeroftheplatform, robustinfrastructure-
as-code principles mandate fail-safe execution mechanics. Network configurations are intrinsi-

2.2 Evolution of Network Administration Paradigms
Network infrastructure administration has historically relied on manual interventions, charac-
terized by the direct execution of commands on command-line interfaces (CLIs) or proprietary
graphical user interfaces (GUIs). Although these manual processes provide high flexibility for
ad-hoc troubleshooting, they fail to meet the scalability and consistency requirements of mod-
ern enterprise environments. As demonstrated by Benson et al. [1], manual network manage-
ment places a high cognitive burden on system administrators. This burden frequently results
in configuration drift and inconsistent security policy enforcement across distributed systems.
To resolve these challenges, Infrastructure-as-Code (IaC) introduced a structured, pro-
grammatic approach to resource provisioning and lifecycle management. The IaC paradigm
is traditionally divided into two distinct execution methodologies:
•ImperativeParadigm:Theadministratorexplicitlydefinesthesequenceofcommands
and API calls required to reach the desired state (e.g., employing Python scripts or
Ansible playbooks). This methodology requires manual handling of execution ordering
and error recovery.
•Declarative Paradigm:The administrator defines the desired final state of the net-
work resource (e.g., using Terraform configuration files), leaving the underlying orches-
tration engine to automatically compute the transition delta (state graph) and execute
the required mutations. The pioneering work on site configuration engines by Burgess
[5] demonstrated the effectiveness of declarative, autonomous systems in converging con-
figurations toward stable target states.
Despite these programmatic advancements, static declarative IaC frameworks present sig-
nificant limitations when deployed in live, dynamic enterprise network environments. First,
they assume complete ownership over the target device state. If an administrator applies
an out-of-band change directly to a security device—such as blocking a malicious IP address
during an active security incident—the local state file becomes out of sync. A subsequent
execution of the IaC pipeline would overwrite this emergency rule, introducing a security
regression. Second, static configurations lack real-time adaptability, meaning they cannot
dynamically adjust rule ordering or validate state parameters against active, live network

highlighted that a significant portion of deployment failures stem from defective or untested

2.4 Firewall Automation and FortiGate Management
Challenges
Whilegeneralcloudorchestrationplatformsmanageresourcesthatarelargelyorder-independent

stricter constraints. Security gateways enforce access control lists (ACLs) and stateful poli-

•Policy Ordering and Shadowing:Firewall rules are processed sequentially in a top-
down, first-match approach. If a broad rule is mistakenly positioned before a specific
policy, it will "shadow" the specific rule, rendering it obsolete. An automated agent must
ensure that rule insertion happens at the correct index to avoid creating security gaps.

•NAT and Routing Consistency:Modifying a security policy often requires coordi-

•Configuration Drift:Firewalls are critical enforcement points. During security in-

•Operational Criticality:A misconfigured virtual machine affects only that specific

•Verifiability and Self-Healing:If an automated configuration push contains a logical

automatically roll back to the last known stable state.
Because of these domain-specific risks, firewall environments require stronger validation
safeguards than generic cloud systems. We must therefore ensure that the translation of
natural language queries is strictly controlled and verified before execution.

The emergence of Large Language Models (LLMs) has introduced conversational capabilities

translator, converting unstructured text into structured parameter payloads (typically JSON
schemas).
However, introducing probabilistic LLMs directly into critical control planes poses signifi-

•Probabilistic Execution Model:Unlike traditional compilers, LLMs behave prob-
abilistically. The same natural language input can produce syntactically different API

interactive Human-in-the-Loop (HITL) framework.

3.6.3 Lifecycle Management & Transactional Recovery
To maintain database and network state alignment, the orchestrator encapsulates mutations
within aTransactional Execution Loop, implementing a strict try-verify-rollback strategy:
1.Pre-Mutation Snapshot:Captures the target configuration parameters (e.g., current
ruleset ordering, specific policy parameters) and stores them in a localized stack buffer
managed by theSnapshotStoreclass (agent/snapshot.py).
2.Atomic Execution:Applies the API changes directly to the FortiOS REST endpoint.
The REST client enforces a strict 5-second timeout window; connections exceeding this
threshold are aborted to prevent session hanging.
3.Active State Verification:Immediately issues a post-write query to read back the
active state. If the returned state does not match the expected state delta, or if a
connection loss occurs (monitored by HTTP heartbeat pings), the system marks the
transaction as failed.
4.Inverse Rollback:Restores the pre-mutation parameters captured in the snapshot,
reverting the firewall to its last known stable state.

3.6.3.1 Operational Recovery Boundaries and Limitations
While the transactional loop mitigates deployment risks, physical networking constraints in-

4.3.2 Natural Language Understanding and Intent Extraction
The NLU interpreter module (agent/nlu_interpreter.py) serves as the sole and tightly
controlled interface between the user’s natural language input and the deterministic processing
pipeline. It is designed with a fundamental engineering constraint:the LLM output is never
trusted directly.
The module operates in three sequential stages:
1.Prompt Construction:The interpreter builds a structured prompt that embeds the
user’s message alongside the current FortiGate device context (available policies, inter-
faces, address objects, and service groups fetched via live REST API). Injecting live
context is a critical security measure: it bounds the LLM’s operational vocabulary to
actually existing objects, reducing the probability of hallucinated references.
2.JSON Extraction (_extract_json()):The raw API response is not trusted to be
valid JSON. The extraction algorithm first searches for markdown code fences (“‘json
... “‘) using a regular expression scan, since the Mistral model wraps its output in
such blocks. If a fence is found, the content is extracted. If no fence exists, the algorithm
attempts to locate the first{and last}characters to carve out the JSON object. This
dual-path extraction is necessary for robustness across LLM output variations.
3.Structural Normalization (_normalize_dict()):The extracted JSON is mapped
through a normalization table that handles case variations, French synonyms (“activer”
→enable, “désactiver”→disable), and field aliases (src→srcaddr). After normal-
ization, the dict is deserialized into the strongly-typedRawIntentSchemadataclass. Any
field mismatch or missing required key raises aNLUParseError, which is caught by the
orchestrator and surfaced to the user as a clarification request.

4.3.3 Contextual Entity Grounding and Normalization
The grounding engine (agent/nlu_grounder.py) constitutes the primary architectural barrier
against LLM hallucinations. Once the NLU layer produces aRawIntentSchema, the grounding
engine validates every extracted entity (policy IDs, policy names, interface names, address
group names) against the actual, live state of the FortiGate appliance.
The grounding algorithm proceeds as follows for a policy reference:
1.APIQuery:AdirectHTTPGETrequestisdispatchedto/api/v2/cmdb/firewall/policy/<id>.
A 404 response conclusively proves the entity does not exist.
2.Name Resolution (Fuzzy Matching):If a name is provided instead of an ID, the
engine fetches the full policy list via/api/v2/cmdb/firewall/policy/and scores each
candidate against the extracted name using Levenshtein edit distance [15]. A match
is only accepted if the edit distance is below a defined thresholdandthe normalized
candidate names are unique (no ambiguous matches).
3.Issue Registration:Any failed resolution (404 response, no match found, or multi-

GroundedIntentSchema.issueslist. The orchestrator inspects this list after grounding
andblocksexecutionifanyunresolvedissueofkind=“not_found”orkind=“ambiguous”
is present.
Critically, the grounding enginenever raises exceptions to the caller. Its contract is to
always return a fully populatedGroundedIntentSchema, with theis_validflag set toFalse

remains deterministic even in the face of API failures or malformed LLM output.

4.3.6 Transaction Snapshot Store and Rollback Engine
To guarantee transactional safety, the snapshot engine (agent/snapshot.py) implements a
pre-state capture protocol. Before any validated write operation is committed, the engine:
1. Generates a unique, 8-character hexadecimalop_idfor the operation (e.g.,A1B2C3D4).
2. DispatchesanHTTPGETtothetargetresourceendpoint(/api/v2/cmdb/firewall/policy/<id>)
to retrieve the exact current JSON configuration.
3. Persists the pre-state JSON payload to disk in a structured snapshot store, keyed by
op_id.
4. Records the snapshot metadata (timestamp, operation type, target resource,op_id) in
the audit log chain.
If the operator subsequently requests a rollback (rollback lastorrollback A1B2C3D4),
the engine retrieves the persisted pre-state payload and re-posts it to the target endpoint via
HTTP PUT, restoring the firewall resource to its exact pre-mutation state.
A critical architectural constraint governs rollback eligibility:CREATE operations are
not reversible via the snapshot engine. Rolling back a resource creation would dispatch
a DELETE request, which could silently orphan other policy objects or references that were
created in subsequent operations. Instead, the system explicitly blocks rollback of CREATE
operations and instructs the operator to perform manual deletion, ensuring no silent state
corruption.

4.8 Architectural Limitations and Honest Assessment
Engineering realism requires acknowledging the architectural limitations of the current imple-
mentation. These limitations are not defects; they are the natural boundaries of a well-scoped
initial implementation, each representing a concrete direction for future work.
58
---PAGE 71---
4.9. Future Work
•Single-Operator Session Scope:TheAgentSessionobject and its associated state
machine are scoped to a single active administrative session. If two operators simul-
taneously connect to the same Streamlit instance, their session states would interfere.
Enterprise deployment would require session multiplexing or per-user session isolation,
which Streamlit’s multiprocessing model can support through external state stores (e.g.,
Redis).
•Synchronous API Communication:The REST API calls to the FortiGate appli-
ance are currently synchronous. In a high-latency network (WAN-connected remote
appliance), each grounding query could introduce significant response delay. Thehttpx
library used in the implementation supports async operations, making migration to an
asyncio-based concurrent pipeline a feasible next step.
•Offline Dependency:The deterministic engine relies entirely on live FortiGate API
responses for entity grounding and pre-state capture. If the appliance is unreachable,
the orchestrator cannot validate any write intent and degrades to a read-only, cached-
context mode. A local state cache with time-to-live (TTL) expiry would mitigate this
dependency.
•Context Window Scalability:The NLU prompt injector feeds the live FortiGate
policy list into the LLM context window for grounding hints. On enterprise appliances
with hundreds or thousands of policies, this injection would exceed the model’s context
limit. A pagination or hierarchical pre-filtering step is required for production scale.
•Rollback of CREATE Operations:As discussed in Section 4.3.6, CREATE op-
erations are not automatically reversible by the snapshot engine to prevent orphaned
reference chains. This is a deliberate, conservative design decision rather than a techni-
cal limitation.
