\chapter{State of the Art and Theoretical Background}

\section{Introduction}
The integration of conversational artificial intelligence into network orchestration represents a major technological paradigm shift in infrastructure engineering. The transition toward intent-driven networking (Intent-Based Networking or IBN) requires a comprehensive understanding of automation paradigms, semantic modeling, and formal validation. The primary objective of this chapter is to establish a rigorous theoretical foundation and conduct a structured review of the current state of the art in network automation technologies.

First, we will analyze the historical evolution of network administration paradigms, tracing the path from manual interventions using command-line interfaces (CLIs) to imperative and declarative Infrastructure-as-Code (IaC) architectures. Second, we will detail the core foundations of Intent-Based Networking, exploring its closed-loop feedback control loop. Third, we will introduce a dedicated discussion on the specific challenges associated with firewall automation and FortiGate management. Fourth, we will study the contribution of Large Language Models (LLMs) in translating natural language intent into structured system payloads, while identifying their semantic limitations and the necessity of a deterministic control plane to guarantee the operational safety of network security appliances. Finally, we will present a comparative analysis of these orchestration models to justify our hybrid design.

\section{Evolution of Network Administration Paradigms}
Network infrastructure administration has historically relied on manual interventions, characterized by the direct execution of commands on command-line interfaces (CLIs) or proprietary graphical user interfaces (GUIs). Although these manual processes provide high flexibility for ad-hoc troubleshooting, they fail to meet the scalability and consistency requirements of modern enterprise environments. As demonstrated by Benson et al. \cite{benson2009network}, manual network management places a high cognitive burden on system administrators. This burden frequently results in configuration drift and inconsistent security policy enforcement across distributed systems.

To resolve these challenges, Infrastructure-as-Code (IaC) introduced a structured, programmatic approach to resource provisioning and lifecycle management. The IaC paradigm is traditionally divided into two distinct execution methodologies:
\begin{itemize}
    \item \textbf{Imperative Paradigm:} The administrator explicitly defines the sequence of commands and API calls required to reach the desired state (e.g., employing Python scripts or Ansible playbooks). This methodology requires manual handling of execution ordering and error recovery.
    \item \textbf{Declarative Paradigm:} The administrator defines the desired final state of the network resource (e.g., using Terraform configuration files), leaving the underlying orchestration engine to automatically compute the transition delta (state graph) and execute the required mutations. The pioneering work on site configuration engines by Burgess \cite{burgess1995site} demonstrated the effectiveness of declarative, autonomous systems in converging configurations toward stable target states.
\end{itemize}

Despite these programmatic advancements, static declarative IaC frameworks present significant limitations when deployed in live, dynamic enterprise network environments. First, they assume complete ownership over the target device state. If an administrator applies an out-of-band change directly to a security device—such as blocking a malicious IP address during an active security incident—the local state file becomes out of sync. A subsequent execution of the IaC pipeline would overwrite this emergency rule, introducing a security regression. Second, static configurations lack real-time adaptability, meaning they cannot dynamically adjust rule ordering or validate state parameters against active, live network metrics. Additionally, an empirical study of configuration scripts by Rahman and Williams \cite{rahman2018characterizing} highlighted that a significant portion of deployment failures stem from defective or untested declarative code.

\section{Intent-Based Networking (IBN) Foundations}
Intent-Based Networking (IBN) redefines how networks are orchestrated by replacing low-level device configurations with high-level, abstract human intentions. According to the comprehensive survey by Leivadeas and Falkner \cite{leivadeas2022survey}, an IBN system is a software platform capable of automatically translating high-level business policies into exact, concrete device configurations, while continuously verifying that the active state matches the requested intent.

The structural architecture of a mature IBN system is designed around a continuous closed-loop control system composed of four sequential phases:
\begin{enumerate}
    \item \textbf{Translation (Ingestion):} Capturing abstract human intent and performing semantic validation against existing infrastructure objects.
    \item \textbf{Activation (Orchestration):} Computing the target configuration, allocating resources, and executing modifications via REST APIs.
    \item \textbf{Verification (Audit):} Analyzing real-time telemetry to ensure that the physical infrastructure state matches the intended design.
    \item \textbf{Remediation (Correction):} Executing automated rollback or repair scripts if a state drift or compliance violation is detected.
\end{enumerate}

This persistent feedback loop ensures that the network continuously aligns with organizational security postures.

\section{Firewall Automation and FortiGate Management Challenges}
While general cloud orchestration platforms manage resources that are largely order-independent (such as compute instances or storage buckets), firewall automation operates under much stricter constraints. Security gateways enforce access control lists (ACLs) and stateful policies, introducing several complex challenges that any automated system must address:
\begin{itemize}
    \item \textbf{Policy Ordering and Shadowing:} Firewall rules are processed sequentially in a top-down, first-match approach. If a broad rule is mistakenly positioned before a specific policy, it will "shadow" the specific rule, rendering it obsolete. An automated agent must ensure that rule insertion happens at the correct index to avoid creating security gaps.
    \item \textbf{NAT and Routing Consistency:} Modifying a security policy often requires coordinating changes in Network Address Translation (NAT) rules, Virtual IPs (VIPs), and routing tables. A mismatch between these components can lead to immediate packet drops or expose internal networks.
    \item \textbf{Configuration Drift:} Firewalls are critical enforcement points. During security incidents, administrators frequently apply temporary, out-of-band rules directly to the appliance CLI or GUI. These manual changes disrupt static configuration templates, making live synchronization and drift detection essential.
    \item \textbf{Operational Criticality:} A misconfigured virtual machine affects only that specific host, whereas a misconfigured core firewall policy can disconnect an entire subnet, disrupt corporate VPN gateways, or expose sensitive database segments to the public internet.
    \item \textbf{Verifiability and Self-Healing:} If an automated configuration push contains a logical error that blocks administrative traffic (such as disabling the management interface or blocking the REST API port), the system must detect this loss of connectivity and automatically roll back to the last known stable state.
\end{itemize}

Because of these domain-specific risks, firewall environments require stronger validation safeguards than generic cloud systems. We must therefore ensure that the translation of natural language queries is strictly controlled and verified before execution.

\section{Conversational AI and LLMs in Network Automation}
The emergence of Large Language Models (LLMs) has introduced conversational capabilities into network administration. Instead of memorizing proprietary syntax or writing complex files, administrators can declare intent using natural language. The LLM serves as a semantic translator, converting unstructured text into structured parameter payloads (typically JSON schemas).

However, introducing probabilistic LLMs directly into critical control planes poses significant operational and security challenges:
\begin{itemize}
    \item \textbf{Probabilistic Execution Model:} Unlike traditional compilers, LLMs behave probabilistically. The same natural language input can produce syntactically different API payloads, introducing unpredictable execution behaviors. As evaluated in the NetConfEval framework by Wang et al. \cite{wang2024netconfeval}, LLMs frequently struggle to generate syntactically accurate network configs under real-world infrastructure constraints.
    \item \textbf{Hallucination Vulnerabilities:} Probabilistic models can hallucinate invalid IP addresses, non-existent interfaces, or deprecated API arguments. These errors can cause severe outages if executed without verification.
    \item \textbf{Lack of Real-Time Infrastructure Context:} Static language models cannot query active firewall state. This limitation can cause them to generate configurations that conflict with pre-existing security policies or shadow routing rules.
\end{itemize}

To systematically mitigate these vulnerabilities, Retrieval-Augmented Generation (RAG), pioneered by Lewis et al. \cite{lewis2020rag}, is integrated as a core architectural building block. By coupling the language model with a vector database containing indexed FortiOS REST API documentations, RAG forces the model's outputs to remain strictly grounded. Empirical studies by Shajarian et al. \cite{shajarian2024rag} confirm that RAG-enhanced architectures substantially improve log analysis, troubleshooting accuracy, and documentation query resolutions in network operations.

Nonetheless, even with RAG, a language model remains a probabilistic engine. It cannot guarantee 100\% syntactic correctness or rule compliance. For this reason, conversational AI alone is insufficient for security-critical environments. A hybrid architecture is required, separating the probabilistic interpretation interface from a deterministic validator that enforces safety rules before the configuration is applied.

\section{Human-in-the-Loop (HITL) and Verification}
In high-security enterprise environments, fully autonomous execution without human verification represents a significant risk of unintended service disruption. The exhaustive analysis of major internet service failures by Oppenheimer et al. \cite{oppenheimer2003why} demonstrates that human oversight errors and blind automation are primary drivers of system outages. To ensure security, it is critical to position the administrator at the center of the decision-making cycle via an interactive Human-in-the-Loop (HITL) framework.

The HITL architecture, as conceptualized by Gómez-Carmona et al. \cite{gomez2024hitl}, embeds strict, interactive validation steps. Within our proposed system, the deterministic Python control plane first validates the syntax and compliance of the JSON intent generated by the AI. If the payload is verified, the system generates a visual configuration diff and requests explicit administrative authorization before executing any changes on the physical firewall.
